# 玄机万象 · 软件项目全生命周期管理平台 · 理念设计

> 版本 v0.2（草案）· 2026-10-12
> 定位：把玄机万象从「通用工作流/Agent 编排平台」深化为「**软件项目全生命周期管理平台**」。
> **核心纠正（v0.2）**：workspace 从一开始就应该是「**项目**」的概念，天然包含多个工作节点（讨论、需求、架构、开发、测试、发布），而不是「一个 workspace 绑定单个 workflow」。
> 本文是理念与领域设计，落地细节见 `docs/detail/` 与迁移脚本。

---

## 0. 一页纸总览

**一句话**：**workspace 即项目——一个项目天然包含多个工作节点（讨论、需求、架构、开发、测试、发布）；每个工作节点 = 一个阶段工作流 + 一份留档 + 一个职能角色；节点之间靠留档衔接。**

**核心主张（四条）**

| # | 主张 | 含义 |
|---|---|---|
| 1 | **workspace 即项目** | workspace 不是"绑定一个 workflow 的执行容器"，而是"承载一个项目全生命周期的容器"，天然包含多个工作节点 |
| 2 | **工作节点即阶段** | 讨论、需求、架构、开发、测试、发布，每个工作节点都是一条可编排、可执行、可复用的阶段工作流 |
| 3 | **留档即衔接** | 每个工作节点的产出物落盘为文件留档，既是本节点交付物，也是下一节点输入——节点之间靠留档衔接，不靠口头交接 |
| 4 | **创建与加载双线路** | **创建新项目**（模板驱动，一次性生成节点链）与**加载既有项目**（进入节点链继续推进）是两条不同的线路，入口、交互、数据流各自独立 |

**与现有平台的关系**：不是推翻重来，而是**重构 workspace 的语义**——把"单绑定"（一个 workspace 绑一个 workflow/agent）升级为"项目容器"（一个 workspace 含多个工作节点）。工作流引擎、Agent、资产版本化、决策门、数据源连接器全部复用。

## 1. 理念定位

### 1.1 核心纠正：workspace 的语义重构

当前 workspace 是「执行交互容器 + 授权边界」，**绑定单个 workflow 或 agent**（`binding_type` + `bound_asset_id` + `bound_asset_version` 三列，二选一）。

本理念的纠正：**workspace 从一开始就应该是"项目"**——它天然包含多个工作节点，每个节点是一个阶段工作流。

```
workspace（项目）
  ├── id / name / root_path（项目文件留档根目录）
  ├── status（DRAFT / ACTIVE / ARCHIVED）
  ├── created_by / org_id（数据权限）
  └── nodes[]（工作节点，有序）
        ├── 讨论节点   → 绑定 workflow A（可行性讨论）  → 留档：可行性报告
        ├── 需求节点   → 绑定 workflow B（需求分析）    → 留档：需求规格
        ├── 架构节点   → 绑定 workflow C（架构设计）    → 留档：架构文档
        ├── 开发节点   → 绑定 workflow D（开发）        → 留档：代码/审查
        ├── 测试节点   → 绑定 workflow E（测试）        → 留档：测试报告
        └── 发布节点   → 绑定 workflow F（发布）        → 留档：发布记录
```

### 1.2 为什么这是更本质的设计

- **项目是天然的组织单元**：软件研发的客观现实是"一个项目经历多个阶段"，而不是"一个工作区跑一个流程"。workspace 作为项目容器，才符合用户心智。
- **避免"补丁式"设计**：旧方案（v0.1）在 workspace 外另建 project_stage 表，把阶段"挂"到 workspace 下——这是打补丁，workspace 语义仍是"单绑定"，阶段是外挂的。新方案让 workspace 本身就是项目，工作节点是它的内生子实体，语义自洽。
- **复用现有能力**：工作流引擎（画布+DAG+决策门+Agent）、资产版本化、数据权限、root_path 文件载体全部保留，只重构"绑定"为"多节点"。

### 1.3 与设计文档 1.4（SDLC 旗舰场景）的关系

设计文档 1.4 已定义 SDLC 七阶段，但那是**对接 Jira/禅道/云效三平台连接器**的 DevOps 形态。本理念聚焦**平台内生项目管理**：阶段划分更贴近实际研发流程（讨论→需求→架构→开发→测试→发布），强调文件留档衔接与职能角色分工，不依赖外部平台。两者可共存，未来经连接器打通。

---

### 1.5 创建与加载双线路（关键设计）

workspace 重构为"项目容器"后，**创建新项目**与**加载既有项目**是两条不同的线路，入口、交互、数据流各自独立，不可混为一谈。

### 线路一：创建新项目（模板驱动，引导式）

```
用户点「新建项目」
  → 填项目名 / 选项目模板（决定工作节点链：标准六节点 / 精简 / 自定义）
  → 后端一次性生成节点链（project_work_node 六条，status=NOT_STARTED）
  → 初始化 root_path（项目文件留档根目录）
  → 返回项目 + 节点链 → 前端进入「项目初始化完成」视图
```

- **本质**：从零到一，模板驱动，**一次性生成整个节点链**，不是逐个建节点。
- **数据流**：`POST /api/projects`（body: name + template）→ 后端建 workspace + 批量建 work_node → 返回。
- **交互**：引导式（填信息 → 选模板 → 确认），创建完成后进入项目视图。

### 线路二：加载既有项目（进入工作现场，继续推进）

```
用户从项目列表点开一个已有项目
  → 后端返回项目 + 节点链 + 各节点状态/留档/决策门
  → 前端进入「项目工作现场」视图
  → 用户操作：执行某节点 / 查看留档 / 审批决策门 / 继续推进
```

- **本质**：进入工作现场，**在既有节点链上继续推进**，不是重新创建。
- **数据流**：`GET /api/projects/{id}` → 返回项目 + nodes[]（含每节点 status/留档/决策门）→ 前端渲染节点链。
- **交互**：项目列表 → 点开 → 节点链进度视图 → 操作具体节点。

### 两条线路的对比

| 维度 | 创建新项目 | 加载既有项目 |
|---|---|---|
| 入口 | 「新建项目」按钮 | 项目列表点开 |
| 驱动 | 模板驱动（一次性生成节点链） | 数据驱动（读取既有节点链） |
| 交互 | 引导式（填信息→选模板→确认） | 工作现场（节点链进度→操作节点） |
| 数据流 | POST 建项目+批量建节点 | GET 读项目+节点链 |
| 产物 | 新项目 + 空节点链 | 既有项目 + 节点状态/留档/决策门 |
| 状态 | 项目从 DRAFT 开始 | 项目保持 ACTIVE |

**设计含义**：
- 创建线路**不要求**用户理解"节点链"细节——选模板即可，节点链由模板决定。
- 加载线路**必须**呈现节点链全貌——进度、留档、待审批决策门，让用户知道"项目进行到哪了、下一步做什么"。
- 两条线路共用同一套 workspace/work_node/artifact 数据模型，但**入口、交互、API 各自独立**，避免"创建时还要想节点"和"加载时还要重新配置"的混乱。

## 2. 领域模型

### 2.1 核心实体

```
Workspace（项目）—— 顶层组织单元（复用现有 workspace 表，重构绑定语义）
  ├── id / name / root_path（项目文件留档根目录）
  ├── status（DRAFT / ACTIVE / ARCHIVED）
  ├── created_by / org_id（数据权限）
  └── nodes[]（工作节点，有序）

WorkNode（工作节点）—— 项目内的一个生命周期阶段（新建 project_work_node 表）
  ├── id / workspace_id / seq（节点序号）
  ├── type（DISCUSS / REQUIREMENT / ARCHITECTURE / DEVELOPMENT / TEST / RELEASE）
  ├── name / description
  ├── status（NOT_STARTED / RUNNING / WAITING_APPROVAL / DONE / REJECTED）
  ├── workflow_ref（绑定的阶段工作流，{definitionId, version} 钉住）
  ├── input_refs[]（输入留档引用，来自上游节点）
  ├── output_refs[]（产出留档引用，本节点交付物）
  ├── owner_role（本节点职能角色）
  └── started_at / finished_at

Artifact（留档）—— 工作节点产出物，文件留档（新建 project_artifact 表）
  ├── id / node_id / workspace_id
  ├── name / type（DOC / CODE / REPORT / CONFIG）
  ├── file_path（相对项目 root_path 的物理路径）
  ├── content_md（文档正文，可检索）
  ├── version（留档版本，可追溯）
  └── created_by / created_at
```

### 2.2 实体与现有表的关系（复用优先）

| 新概念 | 复用现有 | 需新建 |
|---|---|---|
| Workspace（项目） | `workspace` 表（name/root_path/created_by/org_id） | 重构：抽离单绑定三列，加 status |
| WorkNode（工作节点） | `wf_definition`（阶段工作流）+ `wf_run`（节点执行） | 新建 `project_work_node` 表 |
| Artifact（留档） | `workspace.root_path`（文件载体）+ `report_snapshot`（快照模式） | 新建 `project_artifact` 表 |
| 阶段工作流 | 现有 workflow 资产（画布编排） | 无（复用） |
| 阶段 Agent | 现有 agent_config（每节点不同 Agent） | 无（复用） |
| 阶段审批 | 现有决策门（gate） | 无（复用） |

**核心重构**：`workspace` 表的 `binding_type`/`bound_asset_id`/`bound_asset_version` 三列（单绑定）**抽离到 `project_work_node` 表**，workspace 变成纯项目容器。每个工作节点持有自己的绑定（workflow_ref）。

## 3. 工作节点定义

每个工作节点 = 一条阶段工作流 + 一份留档 + 一个职能角色。下表定义每个节点的**输入、工作流形态、产出留档、职能角色、依赖关系**。

| 节点 | 输入（上游留档） | 工作流形态（节点编排） | 产出留档 | 职能角色 | 依赖 |
|---|---|---|---|---|---|
| **1 讨论** | 项目意向、背景 | Agent(调研) → Agent(可行性分析) → 决策门(立项评审) | 可行性研究报告 | 产品/PM | — |
| **2 需求** | 可行性报告 | Agent(需求梳理) → Agent(需求规格) → 决策门(需求评审) | 需求规格说明书(PRD) | 产品/BA | 讨论 |
| **3 架构** | 需求规格 | Agent(技术选型) → Agent(架构方案) → 决策门(架构评审) | 架构设计文档(ADR) | 架构师 | 需求 |
| **4 详设** | 架构设计 | Agent(详细设计) → 决策门(详设评审) | 详细设计文档 | 架构师 | 架构 |
| **5 测试用例** | 详设 | Agent(测试用例设计) → Agent(用例评审) | 测试用例（版本化） | 测试 | 详设 |
| **6 开发** | 详设 | Agent(任务拆解) → Agent(代码生成) → Agent(代码审查) | 代码/提交记录/审查报告 | 开发 | 详设 |
| **7 冒烟** | 开发代码 | Agent(冒烟用例) → Agent(执行冒烟) | 冒烟测试报告 | 测试 | 开发 |
| **8 提测** | 测试用例 + 冒烟报告 | 决策门(提测审批) | 提测记录 | 测试/开发 | 测试用例 + 冒烟 |
| **9 测试执行** | 提测 + 测试用例 | Agent(执行测试) → Agent(缺陷报告) | 测试报告/缺陷清单 | 测试 | 提测 |
| **10 发布** | 测试报告 | Agent(发布检查) → 决策门(发布审批) → Agent(部署执行) | 发布记录/回滚预案 | 运维 | 测试执行 |

**依赖关系说明**：
- **并行**：测试用例（依赖详设）与开发（依赖详设）**并行**，互不等待。
- **汇聚**：提测依赖测试用例 + 冒烟两者完成。
- **前置条件**：提测必须**冒烟 case 跑完**（冒烟节点 DONE）才能进入——冒烟未过则提测 BLOCKED。

### 3.1 节点衔接（留档即输入）

```
节点N 完成 → 产出留档落盘（project_artifact）
  → 节点N+1 启动时，工作流输入 = 节点N 的留档引用（input_refs）
  → Agent 读取留档内容作为上下文，继续推进
```

**关键机制**：节点之间不靠人工口头交接，靠**留档引用**衔接。每个节点工作流的 START 节点声明输入 schema，接收上游留档；END 节点声明输出 schema，产出本节点留档。

### 3.2 阶段依赖关系（DAG + 前置条件，核心）

阶段之间的依赖**不是严格串行**，而是**有顺序、有并行、有前置条件**的复杂关系。阶段链是一个 **DAG**（有向无环图），而非线性链。

#### 3.2.1 两种依赖维度

| 维度 | 含义 | 例子 |
|---|---|---|
| **依赖关系**（DAG） | 阶段之间的先后/并行关系——某阶段依赖哪些上游阶段完成 | 测试用例依赖详设，但**可与开发并行** |
| **前置条件**（门槛） | 进入某阶段的**硬性条件**——不满足不能进入 | 开发提测必须**冒烟 case 跑完**才能进入下一阶段 |

#### 3.2.2 阶段依赖 DAG（示例）

```
[讨论] ──→ [需求] ──→ [架构] ──→ [详设]
                                      │
                    ┌─────────────────┤
                    ▼                 ▼
              [测试用例]          [开发]          ← 测试用例与开发并行
                    │                 │
                    └──────┬──────────┘
                           ▼
                      [提测]（前置条件：冒烟 case 跑完）
                           │
                           ▼
                      [测试执行]
                           │
                           ▼
                      [发布]
```

- **顺序依赖**：讨论→需求→架构→详设（严格先后）
- **并行依赖**：测试用例（依赖详设）与开发（依赖详设）**并行**，互不等待
- **汇聚依赖**：提测依赖测试用例 + 开发两者完成
- **前置条件**：提测必须**冒烟 case 跑完**（硬性门槛），否则不能进入测试执行

#### 3.2.3 数据模型含义

```
project_work_node（工作节点）
  ├── id / workspace_id / seq
  ├── type（DISCUSS / REQUIREMENT / ARCHITECTURE / DESIGN / TEST_CASE / DEVELOP / SMOKE / TEST / RELEASE）
  ├── depends_on[]（依赖的上游节点 id，DAG 边）
  ├── preconditions[]（前置条件，如"冒烟 case 通过"）
  ├── input_refs[]（输入留档引用，来自 depends_on 的交付留档）
  ├── output_refs[]（产出留档引用）
  ├── status（NOT_STARTED / BLOCKED / RUNNING / WAITING_APPROVAL / DONE / REJECTED）
  └── ...
```

- **depends_on**：DAG 边，决定节点何时可启动（所有 depends_on 节点 DONE 才可启动）。
- **preconditions**：硬性门槛，不满足则节点 BLOCKED（如冒烟未过，提测/测试执行阻塞）。
- **status 增加 BLOCKED**：前置条件未满足时的状态。

#### 3.2.4 与工作流引擎 DAG 能力的关系

平台工作流引擎已支持 **DAG 拓扑**（Kahn 拓扑排序，多上游汇聚/多下游分支，见黑板 #91）。阶段链的 DAG 依赖**复用同一套拓扑语义**：
- 阶段链本身是一个"宏观 DAG"，每个阶段是一个节点。
- 阶段内部是一个"微观 DAG"（阶段工作流）。
- 宏观 DAG 决定阶段启动顺序，微观 DAG 决定阶段内节点执行顺序。

#### 3.2.5 阶段依赖的判定

- **可启动**：所有 `depends_on` 节点状态 = DONE，且所有 `preconditions` 满足。
- **阻塞**：`preconditions` 未满足（如冒烟 case 未跑完），节点 BLOCKED，等待条件满足。
- **并行**：两个节点互不在对方的 `depends_on` 链上，可同时 RUNNING。

### 3.3 职能角色（每节点不同 Agent + 审批人）

- **职能 = Agent 配置**：每个节点绑定不同的 agent_config（调研 Agent、需求 Agent、架构 Agent、开发 Agent、测试 Agent、发布 Agent），全员可配置、对等协作。
- **职能 = 决策门审批人**：每个节点的决策门（评审）由对应职能角色审批（产品审需求、架构师审架构、运维审发布），挂起等人 → 通过/驳回 → 恢复。
- **职能 = 数据权限**：不同角色对项目留档的可见/编辑权限不同（RBAC + 数据权限四档，复用现有）。

---

### 3.5 阶段-内容-工具映射（核心落点）

每个阶段虽然在同一个项目目录（root_path）下，但**维护的内容不一样**，需要**不同的 Agent 工具能力**去支撑。这是整个理念的落地核心——工具是每个阶段工作流真正干活的能力。

### 3.5.1 阶段-内容映射（项目目录下的内容分区）

```
<workspaceRoot>/<项目名>/          ← 项目 root_path（所有阶段共用）
  ├── 01-project/      项目资料（项目信息、成员、配置、README）
  ├── 02-requirement/  需求资料（PRD、需求规格、用户故事）
  ├── 03-architecture/ 架构文档（ADR、设计文档、技术选型）
  ├── 04-code/         开发代码（源码、构建产物、提交记录）
  ├── 05-test/         测试用例（用例版本、测试报告、缺陷清单）
  └── 06-release/      发布内容（发布记录、回滚预案、部署日志）
```

| 阶段 | 维护内容 | 内容形态 | 版本化方式 |
|---|---|---|---|
| **项目** | 项目资料 | 项目信息、成员、配置、README | 目录 + 文档留档 |
| **需求** | 需求资料 | PRD、需求规格、用户故事 | 文档留档（content_md） |
| **架构+code** | 开发文档和代码 | 架构文档 + 源码 | **git 版本化** |
| **测试** | 测试用例版本维护 | 用例、测试报告、缺陷清单 | 用例版本化（project_artifact.version） |
| **发布** | 发布内容和日志 | 发布记录、回滚预案、部署日志 | 快照留档（report_snapshot） |

### 3.5.2 项目来源的两种形态

创建项目时，项目目录可能来自两种来源，决定初始化线路：

| 来源 | 场景 | 初始化动作 |
|---|---|---|
| **从 git 创建新项目** | 全新项目，尚无代码 | `git init` / `git clone` 模板仓库 → 建目录结构 → 初始化各阶段子目录 |
| **目录已有项目** | 加载既有代码库 | 扫描既有目录 → 识别已有内容（代码/文档）→ 映射到各阶段子目录 → 建留档索引 |

**设计含义**：项目来源影响创建线路的初始化逻辑，但**不影响阶段工作流本身**——无论项目从哪来，各阶段工作流都在项目目录下维护对应内容。

### 3.5.3 阶段-工具映射（每阶段需要的 Agent 工具）

用户明确要求 Agent 工具包含：**git 相关、db 相关、运维服务器相关、文档分析相关**。映射到各阶段：

| 工具类别 | 工具（Tool SPI） | 支撑阶段 | 能力 |
|---|---|---|---|
| **git 相关** | `git.init` / `git.clone` / `git.commit` / `git.branch` / `git.log` | 项目、开发 | 从 git 建项目、代码提交、分支管理、提交历史 |
| **db 相关** | `datasource.query`（已有）/ `db.schema` / `db.migrate` | 架构、开发、测试 | 查库、看表结构、数据迁移 |
| **运维服务器相关** | `server.deploy` / `server.exec` / `server.log` | 发布 | 部署、远程执行、日志查看 |
| **文档分析相关** | `doc.analyze` / `doc.generate` / `doc.summarize` | 需求、架构、测试 | 分析需求文档、生成架构文档、总结测试报告 |
| **文件相关** | `file.read` / `file.write` / `file.search` | 全部 | 读写项目目录文件、搜索内容 |

### 3.5.4 工具与阶段工作流的结合

每个阶段工作流 = 该阶段的 Agent + 该阶段需要的工具集：

```
需求阶段工作流：
  START → Agent(需求Agent, tools=[doc.analyze, file.read, file.write])
            → 决策门(需求评审) → END

开发阶段工作流：
  START → Agent(开发Agent, tools=[git.commit, git.branch, file.read, file.write, db.schema])
            → Agent(代码审查Agent, tools=[file.read, git.log]) → END

发布阶段工作流：
  START → Agent(发布Agent, tools=[server.deploy, server.log, file.read])
            → 决策门(发布审批) → Agent(部署执行, tools=[server.deploy]) → END
```

**关键机制**：工具是 Tool SPI 的可插拔能力（`io.xuanji.core.api.Tool`），一次实现两处可用（画布 ATOMIC 节点 + Agent 可调用函数）。每个阶段工作流通过**绑定该阶段需要的工具**，让该阶段的 Agent 具备对应能力。

### 3.5.5 工具能力矩阵（当前 vs 目标）

| 工具 | 当前状态 | 需新建 |
|---|---|---|
| `datasource.query`（db 查询） | ✅ 已有 | 无 |
| `git.*`（init/clone/commit/branch/log） | ❌ 无 | 新建 GitTool（Tool SPI） |
| `db.schema` / `db.migrate` | ❌ 无 | 新建 DbSchemaTool / DbMigrateTool |
| `server.*`（deploy/exec/log） | ❌ 无 | 新建 ServerTool（运维） |
| `doc.*`（analyze/generate/summarize） | ❌ 无 | 新建 DocTool（文档分析） |
| `file.*`（read/write/search） | ❌ 无 | 新建 FileTool（文件读写） |

**结论**：工具是本次理念落地的**最大增量**——需要新建 git/db/server/doc/file 五类工具（Tool SPI 实现），每个阶段工作流绑定对应工具集。

### 3.6 过程留档 vs 交付留档（阶段交接语义，核心）

每个阶段内部有自己的**分析过程和碎片化内容**，但**最终只输出一个最终版本**；给到下一个阶段的**一定是最终版本**——下一个阶段**不关注你的过程，只关注你的输出结果**。

#### 3.6.1 两种留档形态

| 形态 | 内容 | 可见性 | 用途 |
|---|---|---|---|
| **过程留档**（碎片化） | 阶段内部的草稿、分析过程、中间产物、讨论记录、Agent 推理轨迹 | **本阶段可见** | 追溯本阶段怎么做的，不跨阶段传递 |
| **交付留档**（最终版本） | 阶段输出的**最终版本**（可行性报告、PRD、架构文档、代码、测试报告、发布记录） | **跨阶段可见** | 下一阶段的输入，阶段交接的唯一载体 |

#### 3.6.2 阶段交接语义（git 式提交）

这个语义与 git 完全同构：

```
阶段N 内部（工作区）：
  Agent 分析 → 碎片化草稿 → 中间产物 → 反复修订     ← 过程留档，本阶段可见
        │
        ▼ 阶段完成时「提交」一个最终版本
阶段N 交付（提交）：
  最终版本落盘为交付留档（project_artifact，version 固化）  ← 下一阶段只读这个
        │
        ▼
阶段N+1 启动：
  输入 = 阶段N 的交付留档（input_refs）
  Agent 只读最终版本，不关心阶段N 内部怎么折腾的
```

**关键规则**：
- **过程留档**：本阶段可见，用于追溯（"这个需求为什么这么定"），不跨阶段。
- **交付留档**：阶段完成时固化版本，是**唯一的跨阶段交接载体**。
- **下一阶段只读交付留档**：不关注上游过程，只关注上游输出结果。

#### 3.6.3 数据模型含义

```
project_artifact（留档）
  ├── id / node_id / workspace_id
  ├── kind（PROCESS 过程留档 / DELIVERABLE 交付留档）   ← 关键区分
  ├── name / type（DOC / CODE / REPORT / CONFIG）
  ├── file_path（相对项目 root_path 的物理路径）
  ├── content_md（文档正文，可检索）
  ├── version（交付留档固化版本；过程留档 version=null 或草稿号）
  ├── status（DRAFT 草稿 / FINAL 最终版本）
  └── created_by / created_at
```

- **过程留档**：`kind=PROCESS`，`status=DRAFT`，`version=null`——本阶段内部，可反复修订。
- **交付留档**：`kind=DELIVERABLE`，`status=FINAL`，`version` 固化——阶段完成时生成，跨阶段传递。
- **input_refs**：节点启动时引用上游节点的**交付留档**（`kind=DELIVERABLE`），不引用过程留档。

#### 3.6.4 与现有 report_snapshot 的关系

现有 `report_snapshot`（看板快照，固化生成时点数据）本质就是"交付留档"的一种——它固化的是报表执行时点的数据。本设计把"交付留档"泛化为所有阶段的最终版本，`report_snapshot` 是发布阶段快照留档的特例。

## 4. 留档机制设计

### 4.1 文件留档（物理载体）

每个项目有 `root_path`（复用 workspace.root_path），节点留档落盘为文件：

```
<workspaceRoot>/<项目名>/
  ├── 01-discuss/可行性研究报告.md
  ├── 02-requirement/需求规格说明书.md
  ├── 03-architecture/架构设计文档.md
  ├── 04-development/（代码仓库/提交记录）
  ├── 05-test/测试报告.md
  └── 06-release/发布记录.md
```

### 4.2 留档元数据（逻辑载体）

`project_artifact` 表记录留档的元数据（名称、类型、路径、版本、归属），与物理文件解耦——**文件在磁盘，元数据在库**，可检索、可追溯、可版本化。

**关键区分（见 3.6）**：留档分**过程留档**（`kind=PROCESS`，本阶段内部，草稿）与**交付留档**（`kind=DELIVERABLE`，阶段完成时固化版本，跨阶段传递）。下一阶段只读交付留档，不关注过程。

### 4.3 留档的三种形态

| 形态 | 载体 | 用途 |
|---|---|---|
| **文档留档** | `project_artifact.content_md` | 可行性报告、PRD、架构文档、测试报告——Agent 生成 + 人工修订 |
| **代码留档** | `root_path` 下代码目录 + git | 开发节点产出，版本化 |
| **快照留档** | `report_snapshot` 模式 | 看板/报表类产出，固化生成时点数据（交付留档特例） |

---

### 4.5 可追溯、可视化、易于交互（体验层要求，贯穿全设计）

每个阶段的步骤和流程**一定可追溯、可视化、易于交互**。这是整个理念的体验层要求，不是某个阶段的附加功能，而是贯穿所有设计的基线。

### 4.5.1 可追溯（全程留痕）

每个阶段的步骤和流程全程留痕，可回溯"项目是怎么走到这一步的"：

| 追溯维度 | 载体 | 内容 |
|---|---|---|
| **阶段执行追溯** | `wf_run`（run 主记录） | 每阶段每次执行的状态、输入输出、触发方式、时间 |
| **节点执行追溯** | `wf_node_run`（节点执行记录） | 阶段内每个节点的状态、输入输出、错误、时间 |
| **决策追溯** | `wf_decision`（决策记录） | 决策门审批历史（谁、何时、通过/驳回、理由） |
| **留档追溯** | `project_artifact`（留档元数据） | 每阶段产出留档的版本、归属、时间 |
| **过程追溯** | `project_artifact`（kind=PROCESS） | 阶段内部的分析过程、碎片化草稿、中间产物 |
| **实时追溯** | `RunEventBus` SSE | run 生命周期事件流（suspended/resumed/finished） |

### 4.5.2 可视化（阶段链 + 节点执行 + 留档树）

| 可视化视图 | 内容 | 复用现有 |
|---|---|---|
| **阶段链 DAG 图** | 项目全流程节点链（顺序/并行/汇聚/前置条件），每节点状态着色 | 复用画布（LogicFlow） |
| **节点执行状态** | 阶段内节点执行进度（RUNNING/SUCCESS/FAILED/SUSPENDED） | 复用 run 详情页节点状态回显 |
| **留档树** | 项目目录下的留档结构（各阶段子目录 + 文档/代码/快照） | 复用文件树 |
| **决策门状态** | 待审批决策门、已审批历史 | 复用决策门卡片 |
| **实时进度** | run 生命周期实时推送（SSE） | 复用 RunEventBus 前端订阅 |

### 4.5.3 易于交互（节点操作 + 审批 + 留档查看）

| 交互 | 内容 | 复用现有 |
|---|---|---|
| **节点操作** | 执行某节点 / 查看节点详情 / 查看节点留档 | 复用工作区 run 触发 |
| **决策门审批** | 待审批决策门：通过/驳回/调整参数 | 复用决策门审批 |
| **留档查看** | 查看某阶段交付留档 / 过程留档 | 复用文档查看 |
| **阶段切换** | 在阶段链 DAG 图上点选节点，进入该阶段工作现场 | 复用画布节点点选 |

### 4.5.4 设计含义

- **可追溯是数据层要求**：所有执行、决策、留档都落库留痕，不丢失过程。
- **可视化是展示层要求**：阶段链 DAG、节点执行状态、留档树、决策门状态都要可视化呈现。
- **易于交互是操作层要求**：节点操作、审批、留档查看都要低门槛、直观。
- **三者复用现有能力**：画布（LogicFlow）、run 详情、决策门、SSE 事件流、文件树——平台已有可视化/追溯基础，本理念把它们**系统化地组织到"项目全流程"视角**。

## 6. 落地路径

### 阶段 A：workspace 重构 + 数据模型（核心）
- `workspace` 表抽离单绑定三列（binding_type/bound_asset_id/bound_asset_version），加 status，变纯项目容器
- 新建 `project_work_node` 表（工作节点：type/seq/status/workflow_ref/input_refs/output_refs/owner_role）
- 新建 `project_artifact` 表（留档元数据）
- 迁移脚本 V17（数据迁移：现有 workspace 的单绑定 → 迁移为第一个工作节点）

### 阶段 A2：创建/加载双线路 API（与阶段 A 同步）
两条线路的 API 各自独立，共用同一套数据模型：

```
【创建线路】POST /api/projects
  body: { name, template: "standard" | "minimal" | "custom" }
  → 后端建 workspace + 按模板批量建 work_node（六条，NOT_STARTED）+ 初始化 root_path
  → 返回 { id, name, root_path, nodes[] }

【加载线路】GET /api/projects/{id}
  → 返回 { id, name, root_path, status, nodes[] }
  → 每节点含：type/seq/status/workflow_ref/input_refs/output_refs/owner_role/artifacts[]/pending_decision
  → 前端据此渲染「项目工作现场」：节点链进度 + 留档列表 + 待审批决策门

【节点操作】POST /api/projects/{id}/nodes/{nodeId}/run   （执行某节点）
           GET  /api/projects/{id}/nodes/{nodeId}/artifacts （节点留档）
           POST /api/projects/{id}/nodes/{nodeId}/approve  （决策门审批）
```

- **创建线路**：模板驱动，一次性生成节点链，用户不感知节点细节。
- **加载线路**：数据驱动，返回节点链全貌（进度/留档/决策门），用户进入工作现场。
- 现有 `POST /api/workspaces`（单绑定创建）废弃，`GET /api/workspaces/{id}` 演进为 `GET /api/projects/{id}`。

### 阶段 B：工作节点工作流模板
- 用现有画布编排 6 个节点工作流（讨论/需求/架构/开发/测试/发布）
- 每个节点工作流含 Agent 节点 + 决策门，作为可复用资产发布
- 每个节点工作流绑定该阶段需要的工具集（见 3.5.4）

### 阶段 B2：阶段工具建设（Tool SPI，最大增量）
- 新建 `GitTool`（git.init/clone/commit/branch/log）——从 git 建项目、代码提交
- 新建 `DbSchemaTool` / `DbMigrateTool`（db.schema/db.migrate）——表结构、数据迁移
- 新建 `ServerTool`（server.deploy/exec/log）——运维服务器、部署、日志
- 新建 `DocTool`（doc.analyze/generate/summarize）——文档分析、生成、总结
- 新建 `FileTool`（file.read/write/search）——项目目录文件读写、搜索
- 每个工具实现 `io.xuanji.core.api.Tool`，一次实现两处可用（画布 ATOMIC 节点 + Agent 可调用函数）

### 阶段 C：节点衔接与执行（过程/交付留档 + DAG 依赖）
- 节点内部：Agent 分析 → 碎片化草稿 → 中间产物 → 反复修订（**过程留档**，kind=PROCESS，本阶段可见）
- 节点完成时：固化**交付留档**（kind=DELIVERABLE，version 固化）落盘 + 登记 project_artifact
- 节点启动时：工作流输入 = 上游节点的**交付留档**（input_refs 只引用 DELIVERABLE，不引用 PROCESS）
- **节点状态机**（NOT_STARTED→BLOCKED→RUNNING→WAITING_APPROVAL→DONE/REJECTED）
  - **可启动**：所有 `depends_on` 节点 DONE，且所有 `preconditions` 满足
  - **阻塞**：`preconditions` 未满足（如冒烟未过），节点 BLOCKED，等待条件满足
  - **并行**：互不在对方 `depends_on` 链上的节点可同时 RUNNING（如测试用例与开发）
- **下一阶段只读上游交付留档，不关注上游过程**

### 阶段 D：前端项目看板（双线路 + 可追溯/可视化/交互）
- **创建线路**：新建项目页——填项目名 + 选模板（标准六节点/精简/自定义），引导式，创建完成后进入项目视图
- **加载线路**：项目详情页——节点链进度（每节点状态/留档/决策门），点开节点进入工作现场（执行/查看留档/审批）
- **可视化**：阶段链 DAG 图（顺序/并行/汇聚/前置条件，每节点状态着色），点选节点进入该阶段工作现场
- **可追溯**：每阶段聚合 run 执行记录 + 节点执行记录 + 决策审批历史 + 留档版本（过程/交付）
- **易于交互**：节点操作（执行/查看留档/审批决策门）、阶段切换（DAG 图上点选）、实时进度（SSE）
- 复用现有画布、资产、工作区页面

### 阶段 E：职能角色深化
- 节点-角色绑定，不同角色对留档的权限差异
- 每节点专属 Agent 配置模板

## 7. 风险与待决

| # | 风险/待决 | 说明 |
|---|---|---|
| 1 | workspace 重构的兼容性 | 现有 workspace 单绑定数据需迁移到第一个工作节点；前端工作区页面需适配"项目容器"语义。**倾向保留 workspace 表结构（加列不加删），单绑定数据迁移为节点**，待确认 |
| 2 | 创建/加载双线路的边界 | 创建线路（模板驱动）与加载线路（数据驱动）必须各自独立，但共用数据模型。**倾向创建线路只做"建项目+生成节点链"，加载线路才做"节点操作"**，避免创建时混入节点执行逻辑 |
| 3 | 阶段依赖的复杂度 | 阶段依赖是 DAG（顺序/并行/汇聚/前置条件），非严格串行。**倾向复用工作流引擎既有 DAG 拓扑语义**（Kahn 拓扑排序），阶段链用 depends_on + preconditions 表达，P0 先支持顺序+并行，前置条件（BLOCKED）后续补 |
| 4 | 留档文件 vs 元数据一致性 | 文件在磁盘、元数据在库，需约定"登记即落盘"的原子语义 |
| 5 | 过程/交付留档的边界 | 过程留档（本阶段可见）与交付留档（跨阶段传递）必须清晰区分。**倾向 process 留档不跨阶段、交付留档固化版本才可被 input_refs 引用**，避免过程碎片污染下游 |
| 6 | 工具建设的范围 | git/db/server/doc/file 五类工具是最大增量。**倾向 P0 先做 file + git（项目/开发阶段必需），db/server/doc 后续补**，避免一次铺太大 |
| 7 | 节点工作流模板的通用性 | 6 个节点模板是"参考实现"，不同团队可自定义节点工作流（节点即资产，可复用可演进） |
| 8 | 与 1.4 SDLC（对接 Jira/禅道/云效）的关系 | 本理念是平台内生项目管理，1.4 是外部工具链对接，未来经连接器打通 |
| 9 | 可追溯/可视化/交互的深度 | 阶段链 DAG 图、节点执行状态、留档树、决策门状态都要可视化。**倾向复用现有画布（LogicFlow）+ run 详情 + 决策门 + SSE，系统化组织到"项目全流程"视角**，不新建可视化引擎 |

## 8. 一句话总结

**workspace 即项目——一个项目天然包含多个工作节点（讨论、需求、架构、详设、测试用例、开发、冒烟、提测、测试执行、发布）；节点之间是 DAG 依赖（顺序/并行/汇聚/前置条件），如测试用例与开发并行、提测必须冒烟 case 跑完；每个工作节点是一条可编排的阶段工作流，内部有自己的分析过程与碎片化内容（过程留档），但最终只固化一个最终版本（交付留档）作为下游节点输入——下游只读最终版本，不关注上游过程；每阶段维护一类特定内容，由不同 Agent 工具（git/db/server/doc/file）支撑；创建新项目（模板驱动）与加载既有项目（进入工作现场）是两条独立线路；每个阶段的步骤和流程全程可追溯、可视化（阶段链 DAG 图）、易于交互（节点操作/审批/留档查看）——复用现有全部引擎能力，只需把 workspace 从"单绑定"重构为"项目容器"，新建"工作节点-留档"组织模型，并建设阶段工具。**
