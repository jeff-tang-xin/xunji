# 运维阶段规范

> 适用范围：项目「运维阶段」（OPERATE）。该阶段是**常驻**的，不可回退到需求/开发阶段，
> 但可以反复发起迭代（一轮迭代 = 一次新需求或一批缺陷的处置过程）。
> 本规范约束**必须满足什么**；每轮迭代内部怎么拆子任务，由 PM 按分诊结论现场规划。

## 一、阶段目标

保证线上可用性与数据安全的前提下，持续消化新需求与缺陷。
核心不是"快"，而是**每次变更都可解释、可观测、可回滚**。

## 二、人工门红线（不可由 AI 或规划降级）

凡具备**生产副作用**的动作，必须人点头后才执行，规划里写成自动也一律抬回人工门：

- 远程服务器执行命令、重启服务、替换部署包
- 生产数据库写入、结构变更、数据修复
- 发布、回滚、灰度批次推进
- 对外发送（通知、报表、调用第三方写接口）
- 删除或覆盖任何存量数据

AI 的职责是**给出决策建议与证据**，人的职责是**批准或驳回**。驳回时必须写理由，AI 带理由重新决策。

## 三、发布门禁（发布前逐条确认）

- [ ] 变更内容、影响范围、回滚方式已写入发布单
- [ ] 数据库迁移脚本就绪，且向后兼容（先加列后删列）
- [ ] 冒烟与全量测试有量化报告，P0/P1 缺陷为零或有延后批准记录
- [ ] 配置项变更清单明确（新增/修改/默认值），与环境一致
- [ ] 观测指标与停止阈值事先约定
- [ ] 回滚经过演练或可行性验证（含数据回滚路径）
- [ ] 相关方已知会发布窗口

任一项缺失，发布子任务不得启动。

## 四、发布执行

- **窗口**：避开业务高峰与无人值守时段；周五与节假日前默认不发布（除非有批准的例外）。
- **灰度**：按批次推进（如 1% → 10% → 50% → 100%），每批次之间有观察期。
- **停止阈值**：错误率、P99 延迟、核心业务量下跌幅度，事先写明数值。越线**立即停止并回滚**，不讨论、不拖延。
- **批次留痕**：每批次的开始时间、结束时间、观测数据、是否推进，逐条记录。

## 五、线上观察

发布后至少覆盖一个完整业务周期。观察项：

- 错误日志新增类型与频次
- 接口成功率与延迟分位
- 核心业务量（下单、支付、对账等）与同比环比
- 数据一致性校验（对账类业务必须跑校验任务）
- 资源水位（连接池、磁盘、内存、慢查询）

观察结论要写"看了什么、数据是多少、是否正常"，不接受"未发现异常"这种无依据表述。

## 六、告警响应

- 告警必须有处置记录：接手人、判定、动作、结果。
- 重复告警同一根因未消除时，登记为缺陷并进入分诊流程，不能一直靠人工压制。
- 处置动作若涉及生产副作用，回到第二节的人工门要求。

## 七、缺陷受理与分诊

**先调查，再决策。** 不接受"看起来像代码问题就直接改代码"。

### 受理单必填

- 现象描述（用户视角）
- 复现步骤 / 期望结果 / 实际结果
- 环境与版本（时间窗口、影响用户范围、是否可稳定复现）
- 严重级别初判

### 调查要求

- 日志：定位到具体请求与堆栈，摘录关键片段作为证据
- 数据：核对实际数据分布，确认是逻辑问题还是数据问题
- 配置：比对变更前后配置与环境差异
- 变更关联：查最近发布/配置变更/数据变更时间线，判断是否与现象吻合

### 分诊结论（五类，必须择一）

| 结论 | 适用条件 | 后续动作 |
|------|---------|---------|
| 代码缺陷 | 逻辑错误，有堆栈或确定性复现 | 走修复子链：编码 → 测试 → 发布（人工门）→ 观察 |
| 配置问题 | 配置错误或环境差异 | 改配置（人工门）→ 验证 → 补配置基线 |
| 数据修复 | 存量数据错误，代码逻辑正确 | 修复方案 + 影响范围 + 反向脚本（人工门）→ 执行 → 校验 |
| 非缺陷关闭 | 符合设计或需求本意 | 说明依据，必要时补文档 |
| 无法复现待观察 | 证据不足 | 写明观察指标与观察期，到期给结论 |

**分诊决策由 AI 给出，必须附证据；人批准或驳回。驳回要写理由，AI 带理由重新分诊。**

## 八、代码缺陷修复子链

复用开发阶段的门禁，不能因为是"线上小修"就跳过：

- 根因分析（写清触发条件，不只是"改了这行就好了"）
- 修复实现 + 回归用例（该缺陷场景必须新增一条用例，防止再次引入）
- 冒烟通过
- 发布（人工门，按第四节的窗口与灰度要求）
- 线上观察确认

紧急止血允许先行回滚或降级，但**回滚不等于修复完成**，缺陷单继续走到根因闭环。

## 九、数据修复规范

- 修复前：影响行数预估、备份或反向脚本、验证查询语句
- 修复中：分批执行，每批可中断；禁止无 WHERE 的 UPDATE/DELETE
- 修复后：验证查询结果、业务侧确认、留档到本阶段产物
- 根因：必须回答"为什么会产生脏数据"，否则同一问题会以不同形态再来一次

## 十、迭代收口（一轮迭代结束前）

- [ ] 本轮受理的缺陷/需求全部有结论（修复、延后、关闭、待观察）
- [ ] 待观察项有明确到期时间与判定指标
- [ ] 发布与数据修复均有完整留痕（谁批准、执行时间、观测结果）
- [ ] 配置基线与文档已同步更新
- [ ] 遗留项写入收口总结，未清项需人显式豁免

## 十一、常见坑

- **跳过调查直接改代码**：改了没修到根因，故障反复出现，且掩盖了真实原因（常见于配置与数据问题）。
- **回滚当修复**：回滚后缺陷单被关闭，根因从未解决。
- **观察期口头确认**：没有数据记录，下次同类变更仍无判断依据。
- **数据修复不留反向脚本**：修错了无法退回，只能再修一次。
- **紧急发布绕过门禁**：事后不补记录，门禁形同虚设。紧急发布可以压缩观察期，但不能省略回滚方案与留痕。
