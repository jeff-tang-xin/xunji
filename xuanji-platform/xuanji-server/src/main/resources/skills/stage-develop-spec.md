# 开发阶段规范

> 适用范围：项目「开发阶段」（DEVELOP）内的所有子任务，含技术方案、设计、编码、自测、提测与测试执行。
> 本规范约束**必须满足什么**。子任务怎么拆、哪些环节可并行、谁参与，由 PM 按技术风险现场决定；
> 但契约先行、冒烟不过不提测、P0/P1 缺陷必须闭环这几条门禁不可由规划裁剪。

## 一、阶段目标

把已批准的需求转成**可运行、可验证、可回滚**的实现，并留下足以支撑运维阶段的文档与数据变更脚本。

## 二、必须产出

| 产出 | 要求 |
|------|------|
| 技术方案 | 模块划分、依赖方向、关键取舍；有争议或不可逆的取舍必须写成 ADR |
| 接口契约 | URL、方法、入参、出参、错误码、幂等语义、鉴权要求 |
| 数据模型与迁移脚本 | 表结构、索引、迁移脚本随代码提交，向后兼容 |
| 测试用例集 | 需求 × 用例矩阵，覆盖正常、边界、异常 |
| 实现代码 | 通过编译与单测，提交即带测试 |
| 冒烟结果 | 主链路最小集执行记录，作为提测前置 |
| 测试报告 | 量化结论，不允许只写"测试通过" |

## 三、架构决策记录（ADR）

不可逆或影响面大的取舍必须留 ADR，四段缺一不可：

- **背景**：当前约束是什么（性能、团队、存量数据、外部依赖）
- **备选**：至少两个可行动选项，各自代价
- **决定**：选哪个，为什么
- **后果**：正面与负面影响，未来什么情况下需要推翻

只给结论不给备选的 ADR 无效——它无法让后来人判断"当时是不是漏考虑了"。

## 四、接口契约规范

- 契约先行：先定契约再实现，前后端/服务间并行开发都依赖它。
- 变更流程：**先改文档，再改代码，同步通知测试**。只改代码不改契约文档是最常见的回归事故来源。
- 兼容性：新增字段可以，删除/改语义不行；确需破坏性变更时提供并行期与迁移路径。
- 错误码：业务错误与系统错误分开，错误响应带可定位信息（traceId / 业务单号），不返回堆栈。
- 幂等：写接口必须声明幂等策略（唯一键、token、天然幂等），重试语义要写清。

## 五、数据变更规范

- 迁移脚本纳入版本管理，命名有序号，可重复执行或明确失败即停。
- **先加列后删列**：新代码兼容旧结构，旧代码不被新结构打挂，保证可回滚。
- 大表变更评估锁与耗时，必要时分批、走在线 DDL 或影子表切换。
- 数据修复（DML）必须有：影响范围预估、备份或反向脚本、执行窗口、验证查询。
- 禁止把 `DROP TABLE` / 无 WHERE 的 `UPDATE`/`DELETE` 混在功能迁移里提交。

## 六、编码与提交门禁

- 提交必须通过编译与单元测试，本地跑不过不要推。
- 一次提交对应一个可说明的变更，混合"重构 + 修 bug + 加功能"的提交在回滚时无法取舍。
- 日志：关键分支与外部调用有可定位日志，禁止吞异常后只打印 `e.getMessage()`（丢失堆栈）。
- 配置：环境相关值走配置，不硬编码；密钥、口令一律不入库不入代码。
- 代码评审关注点：正确性、边界处理、并发与幂等、错误处理、可读性、是否引入未评估的依赖。

## 七、测试用例设计

- 用例矩阵：每条需求编号至少对应一条用例，反向也要能追溯（用例 → 需求）。
- 必测维度：
  - 正常路径
  - 边界值（最小、最大、空、超长、特殊字符、时区与夏令时）
  - 异常路径（依赖超时、部分失败、重复提交、并发冲突、权限不足）
  - 数据兼容（存量脏数据、历史版本记录）
- 用例分级与冒烟对应：主链路 P0 用例构成冒烟集。

## 八、冒烟与提测门禁

冒烟范围 = 主链路最小集（能跑通核心业务闭环，不追求覆盖）。

**冒烟不通过不得提测。** 提测单需包含：变更范围、影响面、冒烟执行结果、数据库变更说明、回滚方式。

## 九、缺陷分级与闭环

| 级别 | 定义 | 处理要求 |
|------|------|---------|
| P0 | 主链路不可用、资损、数据错误、安全漏洞 | 立即修复，修复后必须回归并复测根因场景 |
| P1 | 主要功能有明显错误但有替代路径 | 本期修复，或经评审确认延后并留档 |
| P2 | 体验、文案、低频场景问题 | 可延后，进入遗留清单 |

闭环要求：缺陷单必须有复现步骤、期望、实际、环境、级别；修复必须关联具体提交，关闭前由提出人复验。

## 十、测试报告量化要求

必须给出数字，而不是结论性形容词：

- 用例总数 / 执行数 / 通过数 / 失败数 / 阻塞数
- 按需求编号的覆盖情况（哪些需求无用例、哪些用例未执行）
- 缺陷分布（按级别、按模块、按发现阶段）
- 未修复项及其级别与延后决定人
- 明确结论：是否达到发布标准，不达标缺什么

## 十一、阶段收口检查（进入运维阶段前逐条确认）

- [ ] 需求编号 → 用例 → 执行结果可完整追溯
- [ ] P0/P1 缺陷全部关闭，或有经确认的延后决定并留档
- [ ] 冒烟与全量测试均有量化报告
- [ ] 数据迁移脚本就绪且向后兼容，回滚方式已验证或演练
- [ ] 接口契约文档与代码实现一致
- [ ] 关键取舍有 ADR，遗留技术债单独列出
- [ ] 运维交接材料齐备（部署方式、配置项、监控点、已知风险）

## 十二、常见坑

- **契约写完就放着**：实现过程中契约悄悄变了，测试还按旧契约执行，上线才发现不一致。
- **把冒烟当形式**：冒烟只跑一条最顺的路径，提测后主链路依然频繁断裂。冒烟集要覆盖真实主链路分支。
- **迁移脚本与代码同版本不可回滚**：代码回滚了，数据库结构回不去，形成"只能往前修"的死局。
- **测试报告只写结论**：没有数字，无法判断"通过"是 20 条还是 200 条，也无法定位薄弱模块。
- **缺陷复现依赖口头**：提单人关闭前不复验，同一问题反复打开。
