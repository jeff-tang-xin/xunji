# 需求阶段规范

> 适用范围：项目「需求阶段」（REQUIREMENT）内的所有子任务与讨论。
> 本规范约束的是**必须满足什么**，不是**怎么做**——子任务怎么拆、谁参与、什么顺序，由 PM 按项目特征现场规划；
> 但下面的产出清单与验收底线不能裁剪，确实无法满足时必须显式写明理由并留档。

## 一、阶段目标

把模糊的业务诉求谈成**可判定、可实现、可验收**的需求集合，并明确本期边界。

判断本阶段是否达成，只看一件事：开发阶段的参与者拿到这份需求，是否还需要回来追问"这条到底什么意思"。
需要追问，就说明没收口。

## 二、必须产出

| 产出 | 要求 |
|------|------|
| 需求说明书（PRD 或等价文档） | 每条需求有唯一编号，可单独引用与追踪 |
| 验收标准 | 逐条挂在需求编号下，测试可直接执行，不允许"体验良好""性能优化"这类无法判定的表述 |
| 范围外清单（Out of Scope） | 显式列出本期不做什么，以及为什么不做 |
| 非功能要求声明 | 性能、并发、安全、兼容、可观测、数据量级，逐项标注"有要求 / 无要求 / 待定" |
| 优先级与依赖 | P0/P1/P2 分级，并标出需求之间的强依赖顺序 |
| 边界与异常场景清单 | 空值、超长、并发冲突、重复提交、权限越界、部分失败等 |
| 合规与隐私检查条目 | 涉及个人数据、资金、权限、审计日志时必须成文（规范强制项） |

## 三、需求条目写法

每条需求至少包含四段，缺一不算写完：

1. **编号与标题**：`REQ-001 支持批量导入对账明细`
2. **用户故事**：作为〈角色〉，我希望〈能力〉，以便〈价值〉。价值写不出来的需求要质疑其必要性。
3. **验收标准**：Given / When / Then 或「输入 → 期望输出」成对描述。
   - 反例：「导入要快」
   - 正例：`Given 已上传 5 万行合法 CSV，When 点击导入，Then 60 秒内完成并返回成功/失败行数明细`
4. **约束与例外**：数据来源、幂等要求、失败是否可重试、是否需要人工审核。

## 四、优先级判定基准

- **P0**：不做则本期目标不成立，或会造成资损/合规风险。上线必须包含。
- **P1**：影响主要用户的主流程体验，但可用替代路径绕过。本期应尽量包含。
- **P2**：优化项、长尾场景、内部工具便利。可延后，延后要在范围外清单里记一笔。

判定时先问"没有它会发生什么"，答不出后果的，降级或砍掉。

## 五、非功能要求检查清单

逐项确认，**不允许整体留空**（留空视为未考虑，不是视为无要求）：

- 性能：响应时间目标、吞吐目标、慢查询与超时阈值
- 容量：数据量级（当前 + 1 年）、单表规模、归档策略
- 并发：峰值并发、锁竞争点、幂等与去重
- 安全：认证方式、授权粒度、敏感字段脱敏、注入与越权风险
- 兼容：接口向后兼容期、历史数据迁移、老版本客户端
- 可观测：关键指标、日志字段、告警阈值
- 合规与隐私：个人数据类型、留存期限、访问审计、导出限制

## 六、范围外清单怎么写

范围外不是"没想到"，而是"想过并决定不做"。每条包含：

- 内容描述
- 不做的理由（成本、价值、风险、依赖未就绪）
- 重新评估的触发条件（例如"客户量超过 X 时重提"）

这份清单在开发阶段与运维阶段会被反复引用，用来回答"这个是不是本期该做的"。

## 七、多方讨论的收口方式

需求阶段常需要架构、开发、测试、DB 一起参与。讨论结束时必须产出**结论**而不是"大家意见"：

- 每条有争议的需求，标注最终决定 + 决定人 + 反对意见留档
- 未决项单独列出，写明"阻塞在什么、谁负责、什么时候给答案"
- 未决项数量与内容会进入阶段收口总结，非空时推进阶段需要人显式豁免

## 八、阶段收口检查（进入开发阶段前逐条确认）

- [ ] 每条需求有唯一编号，且验收标准可被测试直接执行
- [ ] 非功能要求逐项有结论
- [ ] 范围外清单成文，越界项单独标记
- [ ] 边界与异常场景已列举，高风险项有处理方案
- [ ] 合规与隐私检查条目已成文（涉及个人数据/资金/权限时）
- [ ] 优先级与依赖顺序明确，开发阶段可据此排期
- [ ] 未决项清单为空，或已就遗留风险取得确认

## 九、常见坑

- **把方案当需求**："加一个缓存"是方案，"列表页 1 秒内打开"是需求。写需求阶段不要出现技术选型。
- **验收标准写在文档末尾**：必须逐条挂在需求编号下，否则测试无法覆盖、需求变更时找不到影响面。
- **只写正常路径**：异常与边界场景的缺陷密度远高于正常路径，需求阶段不写清，测试阶段只能靠猜。
- **范围口头约定**：口头说的"这个不做"到验收时一定会被重新提出，必须落到范围外清单。
- **忽略数据来源的真实性**：涉及存量数据的需求，先查实际数据分布（空值率、量级、脏数据比例）再定方案，不要按理想数据设计。
